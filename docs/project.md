# Dotfiles Project Roadmap


## Project History

Dotfiles is a vestigial name that harkens to the days of old-school
development by hand. Dotfiles refers to the period which prefaces the
name of hidden folders in a directory. Developer only.

Since the early days, I've added a number of technologies to my
developer workflow. `docker` is a major one: adding a level of environmental
reproducibility that previously relied on sporadic setup scripts.

`devcontainer` is another layer on top of docker which adds the extra
abstractions necessary for a text editor or IDE to just attach directly
to a code repository, attaching the code directory workspace as a volume to
the docker container.

And of course, we have entered the era of AI agentic coding. While
I initially used Codex as an AI-first development environment, I have
recently switched back to my old `tmux` + `vim` developer setup, with
the addition of `opencode` as an agentic harness.

## Core Components

To be honest, there's quite a bit of this repository that I don't use.
The main components that I do use are:
1. `tmux`: I've edited `tmux.conf` quite a bit to make the keybindings my own
2. `vim`: it's my prefered editor: the keyboard commands are incredible, but
I actually don't have a great handle on which plugins I actually use.
3. `bash`: I mainly just use `bash` as a shell and honestly don't know
the differences between `bash` and `zsh`. The `bashrc` file is mainly
autogenerated, but I've edited `bash_aliases` with some changes.
4. `opencode` is the newest major important dependency: in a currently
open PR I add the `opencode` config directory and my first `github-pr`
skill
5. `infectdots.sh` is the main place that the configs are symlinked and are
part of the critical path
6. `ghostty` is the modern terminal that I've been using at the top level
to handle the intricacies of MacOS integration

The rest of the configurations in this repo I'm less tied to.

## New Directions

While `dotfiles` originally emerged as a repository to version control
the configuration files of developer tooling, I am now envisioning an
extended role. In additional to configs, I'd like to encapsulate
all developer dependencies so they can quickly and easily be installed
on a new machine.

The initial target will be any machine with a `docker` runtime, but I would
like to use `devcontainer` as a uniform environment to perform compilation
to a variety of native platforms, starting with MacOS.

Also, a major idea that I'd like to flush out more deeply is multi-machine
development. `tmux` already has some strong capabilities to work across
machines, and I'd like to leverage it to control a swarm of agents across
multiple machines: personal computers, cloud computers, and eventually even
phones (although that will require a different UI, e.g. voice-centric,
perhaps). 

These features will quite possibly require new additions to the core
components, or perhaps can be implemented via `opencode` plugins for instance.
